## 1. WK-19: rumble goes only to the pad it concerns. PASS

**Method.** `Input.start_joy_vibration` has exactly one call site, `InputRouter.rumble()` (src/core/InputRouter.gd:288). It appends
to `InputRouter.rumble_log` straight after the call, so the log is the call list. A root probe
(`scratchpad/RumbleProbe.gd`, survives change_scene) recorded every `rumble_log` entry and every `smashed` / `super_boosted` /
`bounced_juicy` / `killed` / `powerup_used` / `hazard_shoved` event, tagging each player argument with its device key ("kb",
"pad:N" or "bot"). Real smashes were driven by an in-game driver (`scratchpad/SmashDriver.gd`). It fires real pad / keyboard input
events (stick toward the victim, X or K hold and release) within frames of parking the attacker 110 px from the victim. Seats:
P1 = keyboard, P2 = pad:1, P3 = pad:2, plus one CPU (Meadow Mile, 2 matches, LIVES 1 then 3).

**Results.** With RUMBLE ON the session logged 758 vibration calls and 43 smashes (54 counting the RUMBLE OFF window) (dumps: `scratchpad/r1.json`, `r2.json`, `r3.json`):

| Check | Evidence | Verdict |
|---|---|---|
| Victim's pad gets the full pulse (0.9 / 0.8, 0.10 s) | All **30** smashes with a pad victim produced exactly one 0.9/0.8 call, on the victim's key. Examples: `smash a=pad:1 v=pad:2 @925811 -> pad:2 0.9/0.8`, `a=bot v=pad:2 @967316 -> pad:2 0.9/0.8` | PASS |
| Attacker gets 0.5x (0.45 / 0.40) | All **10** smashes with a pad attacker produced a 0.45/0.40 call on the attacker's key, and nowhere else. Examples: `a=pad:2 v=pad:1 @930394 -> pad:1 0.9/0.8 + pad:2 0.45/0.4`, `a=pad:2 v=bot @930902 -> pad:2 0.45/0.4 only` | PASS |
| Keyboard or bot on either side never buzzes anything | 5 kb-attacker smashes: victim call only. 8 kb-victim smashes: no call. Bot attackers: no attacker call. `"kb"` never reached `start_joy_vibration`, and no call ever went to device 0 (keyboard and joypad 0 are not confused, CC-3.2) | PASS |
| Supers buzz only the firer | Every pad super gave 1.0/0.95/0.25 s on the firer's own key (pad:1 x16, pad:2 x8). kb supers and bot supers: no call | PASS |
| Bounces buzz only the bouncer | 635 bounce pulses (while RUMBLE was ON), every one on the bouncing goat's own key | PASS |
| Cross-check | For each of the 758 calls I looked for an event within 34 ms that names the same device. Calls with no match: **0** | PASS |
| RUMBLE OFF = zero calls | Turned off through the real UI (keyboard: Esc -> OPTIONS -> RUMBLE, `WK-160_17`). Over the next 8 smashes (6 pad victims, 2 pad attackers), 12 supers and 123 bounces: **0** new `start_joy_vibration` calls, and `rumble_suppressed` rose by 49. Nothing fired while paused (CC-7.4) | PASS |
| RUMBLE ON test pulse | Turned back on from a pause that pad:1 owned (`WK-160_18`). The single 0.5/0.6/0.18 s pulse went to `pad:1` only | PASS |
| Rumble on rebind | Disconnect reclaim and takeover pulse only the new device (`DeviceWatch.rebind`, 0.4/0.6) | PASS (code + log) |

**Feel note (not a WK-19 failure; candidate P3).** Bounce rumble fires on every bounce that launches faster than 310 px/s
(`Juice._on_bounced`, t > 0.25 of 1240). An idle goat's floor bounce launches at 758-929 px/s, so a pad buzzes about once a
second even when its player is doing nothing: pad:2 took ~395 bounce pulses in the session against 16 smash pulses. Over a long
session that numbs the pulses that matter (getting smashed, firing a super). Suggest gating bounce rumble to spring-tier
launches (>= ~1100 px/s) or to bounces out of hitstun. This is a sound-designer / game-designer call.

**Residual risk.** `rumble_player` with an empty `device_key` (legacy cold boot straight into a match scene) rumbles every pad
seen so far. A normal session never reaches it, because the front end always seats a device.

**Close WK-19.** It shipped in 2e406dc (WK-44). Evidence is the table above plus `WK-160_17`, `WK-160_18`.

## 3. WK-28b in-match disconnect + toasts: verdict FIX

Graded against CC-3.4 / 3.5 / 1.5 / 1.6 / 1.7 / 5.1 / 5.7 / 6.1 / 8.1-8.3, with keyboard plus pads 1-5.

**What passes (Ship quality):**
- **Auto-pause** on a live-match pad loss, plate in the lost player's colour with a greyed portrait: "P2 · CONTROLLER ·
  DISCONNECTED", "PLUG IT BACK IN" (`_20`). On reconnect, the portrait recolours and an "IS BACK!" green chip with "WELCOME BACK, P2!"
  shows, but it still waits for A (CC-3.5) (`_21`).
- **All four exits from CC-3.4 work:** A on the lost pad reclaims (`rebind seat1 pad:1->pad:1`, `_22`). A on an unjoined pad takes
  over (pad:3 -> P2). `human_device_keys`, `InputRouter.joined` and `GameConfig.lobby` all follow it (`_23`). Held RESUME WITHOUT P3
  turns the seat into a CPU (InputBot L3) with the HUD sub-tag "CPU" (`_25`). Held QUIT TO MENU lands on mode select with the lobby
  cleared (`_32`, `_33`).
- **CPU seat take-back mid-play:** A on the old pad -> toast "P3 · IS BACK!" in P3 orange (`_26`). New-pad toast "CONTROLLER
  CONNECTED" (`_27`). RESTART with the pad still out starts the seat as a CPU with the toast "P2 · CONTROLLER STILL OUT · PLAYING AS
  CPU" (`_44`).
- **Queue:** two pads lost together -> one plate, plus "P3 IS DISCONNECTED TOO". The take-over of P2 re-arms, then P3's plate shows
  in P3 orange (`_28`, `_29`).
- **Over an open pause menu:** the pause is suspended under the overlay. When the pause owner's pad is taken over by pad:5, the pause
  menu comes back owned by the new pad ("PAUSED · P2", `_owner_key = pad:5`, `_30`, `_31`), as CC-1.5 requires.
- **No drivers left (pads-only match, both lost):** RESUME WITHOUT and the hold hint are hidden. The keyboard, as a free device, sees
  "A / ENTER ... TAKE OVER" and Enter takes P1 (`_42`, `_43`).
- Both destructive choices are holds (CC-6.1). Input is ignored for 0.45 s after the overlay opens. A driver's Esc/B is swallowed
  (no leak into the suspended pause menu). The takeover A is swallowed until release (CC-5.7). Footer twins "A / ENTER Hold to
  confirm" (CC-1.6). Label sizes 28-58 px at 1080p (CC-8.1 minimum met).

**F1 [P1 bug, new S item]: a pad that is still gone comes back as a live lobby seat and blocks launch.**
Repro: 2-human match (kb + pad:2) -> `Input.joy_connection_changed.emit(2, false)` -> hold RESUME WITHOUT P2 -> pause -> CHANGE
SETUP (or REMATCH -> CHANGE SETUP). In the lobby, P2 shows as a normal PICKING "BUTCH · GAMEPAD · A LOCK IN" panel bound to
`pad:2`, which is still in `DeviceWatch._gone` (`WK-160_45`). There is no DISCONNECTED face and no 10 s expiry. READY TO FIGHT
never appears, and the keyboard's Enter does nothing. Nobody can clear the seat, because only pad:2's own B can. The only way
out is for the keyboard to leave its own seat and then hold Esc to quit the lobby. The phantom also follows into the next mode
(ROCKETBALL lobby, `WK-160_47`). On real hardware this happens whenever a pad dies mid-match and the couch later picks CHANGE
SETUP.
Cause: `HerdLobby._restore_lobby` restores PICKING/READY seats from `GameConfig.lobby` without checking whether the device is
still there (`_persist` drops only S_DISC seats).
Fix: in `_restore_lobby`, seat a device that is in `InputRouter/DeviceWatch._gone` (or whose pad id is not connected) as
**S_DISC with a fresh grace window** (goat and colour kept, takeover allowed, expires to EMPTY), exactly like a live disconnect.
Accept: the repro above shows the DISCONNECTED face, and launch is possible after 10 s or after a takeover.

**Polish fixes (one S item):**
- **F2:** the note "P2'S GOAT PLAYS ON AS A CPU" sits 1 px under RESUME WITHOUT. The button's 1.08 focus scale and drop shadow
  overlap it, so it reads muddy grey (`WK-160_20b_overlay_note_zoom.png`). Add >= 12 px gap (or make it the button's sub-line)
  and draw it solid chocolate without the light outline (CC-8.2).
- **F3:** a takeover or reclaim made *inside the overlay* gives no visual confirmation, only a sound. The overlay simply closes,
  and the room can't tell that pad 4 is now P2. Show the same toast the mid-play path uses ("P2 · TAKEN OVER" with the new
  device's icon, or "P2 · IS BACK!").
- **F4:** when no driver is left, QUIT TO MENU is drawn focused, gold, with a hold ring, but no pad or key can trigger it (A means
  TAKE OVER, and the hint strip is hidden) (`_42`). That breaks CC-1.7 / CC-5.1, because it looks actionable and isn't. Draw it
  unfocused in that state, or add the caption "TAKE OVER FIRST TO QUIT".
- **F5:** "P3 IS DISCONNECTED TOO" is all red text. Print each P# token in its identity colour (CC-8.3) (`_28`).
- **F6:** the lobby "CONTROLLER CONNECTED" toast sits on top of the goat roster strip, covering 4 portraits (`_41`). In the lobby,
  drop it below the header row or show it at the bottom.
- **F7 (copy):** when the keyboard twin shows, "ON ANOTHER CONTROLLER TO TAKE OVER" should read "ON ANOTHER CONTROLLER OR KEYBOARD
  TO TAKE OVER" (`_42`).
- Non-blocking: a seated device's B on the overlay is silently swallowed. CC-5.2 says "nothing silently dead", so add a deny
  tick.

**WK-28a lobby half, rendered re-confirm: Ship.** Pad lost while PICKING -> DISCONNECTED face, goat and colour kept, "PLUG IT
BACK IN · 10 ... · 4" with a draining ring around "A TAKE OVER", EMPTY at 10 s (`_34`, `_35`, `_36`). A seat that was READY when
lost blocks READY TO FIGHT while it is DISCONNECTED (Enter doesn't launch, `_37`). The same pad's A restores it to READY. A
different, unjoined pad takes the goat but starts in **PICKING** (`pad:3 PICKING goat 2`, `_38`), which closes the evidence gap
in the 2026-11-15 verdict. If the RULES owner's pad is lost, the flip closes and keeps the edited value (SELF-KO -1 ON kept,
`_39`, `_40`). A newly connected pad only toasts and does not join until it presses A (`_41`).
