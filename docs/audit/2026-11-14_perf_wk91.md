# Perf: WK-91 "16 FPS, 500-620 ms hitches" (Arena.tscn, BRAWL 1 human + 3 bots). 2026-11-14. Branch weekend/polish @ b72b94a + uncommitted tree

**Author:** Performance Analyst. **Verdict:** the game is not slow. WK-91 was measured with the **laptop display
OFF** (Windows Modern Standby). While the display is off, DWM throttles windowed presents to about 30 Hz, and
it adds a ~500 ms present stall every 0.7-2 s. With the display awake, the same build holds a **locked 119.6 fps at 1920x1080
(vsync, 120 Hz panel), with 0 frames over 100 ms**. That run used the stage-load fix described below. Before the fix there was 1 frame over 100 ms in 150 s.
The only real hitch in the game was the stage load on a theme change, up to 149 ms. It is fixed: max frame is now 72 ms.

Caveat: another agent was editing the tree during this pass (PartyMatch.gd, the HUD/legend scenes and others, all uncommitted).
One launch at 15:40 hit their mid-edit `set_labels` arity error and stuck in BOOT. That run is excluded from the figures below.

## Method
- A per-frame recorder was installed via `gbplay eval`. It is now reusable at
  `.claude/skills/gottabounce-diagnostics-and-tooling/scripts/frame_recorder.gd`. It logs every main-loop iteration with these fields:
  `dt` (process-to-process wall time), `steps` + `phys` (wall time from first to last physics tick), `draw`
  (`frame_pre_draw` -> `frame_post_draw`, which includes swap/vsync), the viewport's measured GPU and render-CPU time, draw calls,
  node count, and state + level name for frames over 50 ms. Hitch counts come from this recorder, not from polling.
- Raw JSON for every run is in the session scratchpad and is not kept in the repo. Screenshot of the fixed build:
  `tools/out/wk/WK-91_after_fix_1080p.png` (renders normally).

## 1. Per-frame breakdown (medians)
| Run | fps avg | dt | phys | draw (swap) | GPU | render CPU | scripts+other | draw calls | >100 ms |
|---|---|---|---|---|---|---|---|---|---|
| Display OFF, GL, 1280x720, 65 s | **18.9** | 34.6 | 2.6 | **31.4** | 0.71 | 0.53 | 0.55 | 73 (max 118) | **48** (max 557) |
| Display ON, GL, 1920x1080, 180 s (fixed build) | **119.6** | 8.33 | 1.0 | 6.3 (vsync wait) | 1.64 | 0.59 | 0.9 | 79 (max 117) | **0** (max 72) |

The real work in a frame is about 3 ms out of the 8.3 ms vsync interval. Physics costs ~0.5-1 ms per tick, against a budget of 8.3 ms.
Draw calls (73-124) are far above the old golden figure of 28 because content has grown since then, but they cost about 1.6 ms of GPU time. This is not a bottleneck.
Node counts stayed bounded across 15 stages (399-497, no upward drift).

In the bad state, every 500 ms hitch sits **inside `draw` (the present/swap)**. GPU and render-CPU time stayed under 1 ms in those frames.
That rules out the game's scripts, physics, the MCP server, shader compiles and fill rate. It also explains why 720p and 1080p
looked the same, and why headless runs looked fine (headless never presents a frame).

## 2. Hitch attribution, with A/B evidence

### Cause A (the WK-91 symptom): display off / Modern Standby throttles presentation. ENVIRONMENT, not code
Natural A/B, same build and config: the display woke at **15:50:03**.
| Config (native GL, windowed 1280x720, console exe) | fps | >100 ms frames |
|---|---|---|
| 15:41-15:49, display off (4 fresh launches) | 16.3-20.1 | 15-22 per 25-30 s |
| 15:52-15:57, display on (GUI exe, console exe, fresh relaunch) | 119.0-119.5 | 1-2 per 25 s (stage loads only) |

The ANGLE run happened to straddle the wake. It shows a step in `draw` at t=33.3 s, the exact second of the 507 event.

**Controlled A/B (15:59:47).** The display was turned off via SC_MONITORPOWER during a recording:
- 0-9 s, display on: 117-120 fps.
- At display-off: every frame immediately becomes `draw` 31-33 ms (~25 fps). This is the exact bad-state signature.
- Modern Standby then suspended the process for 180 s (one 180 546 ms frame).
- On wake: ~1 s of 33 ms frames, then 119.8 fps.

Other results gathered during the display-off window, all consistent with DWM composition being throttled:

| Display-off variant | Result |
|---|---|
| Vsync off (GL) | Median 0.98 ms, but still 29 present stalls >100 ms per 40 s |
| ANGLE/D3D11 + vsync | 26.6 fps, stalls gone |
| ANGLE + vsync off | 284 fps, 0 hitches |
| Exclusive fullscreen (bypasses DWM) | 119.8 fps, 0 hitches |
| Vulkan Mobile | 119.1 fps |
| Borderless fullscreen (`Settings` fullscreen) | 18.7 fps |
| Focus/foreground, resize, minimize/restore, borderless round-trip | No change |

So no renderer or settings change is needed for a player whose screen is on.

### Suspects ruled out (each with a measurement)
- **(1) A periodic game system** (powerup director, bot planner, hazards, telemetry, `_mh_*`, Settings writes, log spam).
  The stalls were in `draw`, with GPU and render-CPU time under 1 ms. The `phys` and process segments were normal (2-3 ms) in hitch frames.
  The "every ~15 s" figure was a polling artefact: the recorder shows a stall every 0.7-2 s (48 in 65 s).
  With the display on, the same systems run with 0 hitches over 15 stages.
- **(2) Shader/pipeline compile.** Render-CPU time maxed at 1.8 ms in the bad state. Not present.
- **(3) McpInteractionServer.** Its `_process` work is part of the 0.55-0.9 ms scripts+other column. It is the same code in good and bad runs.
- **(4) vsync / physics.** Vsync off did not remove the stalls in the bad state. Physics is ~1 ms per frame.
  The 8-tick cap only bites because frames were 500 ms long.
- **(5) GPU.** The discrete RX 6700S via OpenGL 3.3, as intended. The power plan is the same in good and bad runs.
- **(6) External load.** A GDI desktop capture every 1.5 s produced 0 hitches (119.6 fps). Dropbox and AV cannot account for
  stalls inside SwapBuffers that toggle exactly with the display state.

### Cause B (a real game cost): stage load on a theme change, 59-149 ms in one physics tick. FIXED
- **Before** (1080p, display on, 150 s): STAGE_INTRO frames of 149 ms (Atoll), 93 (Bumper Gauntlet),
  68 (Singularity) and 97 (Wrecking Yard). All were `phys` time inside `_begin_stage`.
- **Cause, measured directly.** `ArenaRenderer` `load()`s each theme's art synchronously. The previous stage's textures are
  freed, so they drop out of the ResourceCache. A cold load costs about 42-44 ms for each lossless 1536x1024 painting
  (5 themes plus sky_grass_day) and about 11-13 ms for each body/hero strip.
  `LevelLoader.load_level` on a detached root took **50-271 ms per level before the fix and 4.4-34 ms after**.
  The 13 pool levels sum to about 1750 ms before and about 175 ms after.
- **After** (1080p, display on, 180 s, about 7 stage loads): **0 frames over 100 ms, max 72 ms**, with STAGE_INTRO peaks of 62 ms.
  The live WK-21 phase log over 15 stages shows **wall = tick within 0.06 s for every phase**.
  The designed flow of 4.78 s / 6.18 s is met, so WK-21 "1-2 s over budget" was also a display-off artefact.
- **Cost:** about +52 MB of texture memory (117 -> 169 MB `RENDER_TEXTURE_MEM_USED`) for the 22 retained textures. Static RAM is unchanged.

## 3. Fix applied (uncommitted)
`src/systems/ArenaRenderer.gd` (+43 lines). On the first `setup()`, the renderer requests every `res://...png` named in its
own constants (paintings, interiors, bodies, mats, decals, clouds) through `ResourceLoader.load_threaded_request`.
Later `setup()` calls move the finished loads into a static keepalive, so each texture is decoded once per session.
No call sites changed and visual output is identical.
- Parse gate: clean.
- Rendered check: 15 stages and a screenshot, no new errors in stderr.
- Revert: delete the 3 static vars, the `_prewarm_art()` call, and the two helpers.

## Recommendations (backlog form)
1. **[P0][S] Close WK-91 as environment, and harden the tooling.** Owner: Director, plus tooling (gameplay-programmer).
   - (a) Rendered perf, timing and feel numbers are only valid with the display awake.
   - (b) Add a pre-flight to `run_game.ps1`, `perf_gate.py` and the recorder:
     read the latest Kernel-Power 506/507 event; if the last one is 506, print "DISPLAY OFF - timings invalid".
     Also flag runs where median `draw` is 25 ms or more while GPU + render-CPU time is under 3 ms.
   - (c) Ask the owner (machine setup) to set the AC display timeout to Never on the studio laptop, or to wake it before agent sessions.
     Synthetic input does not reliably wake Modern Standby; Godot's `keep_screen_on` only prevents sleep, it does not wake the screen.
2. **[P1][S] WK-90: re-measure hit-stop with the display on.** The "0.75 s at 16 FPS" figure came from the bad state. At 120 fps the
   freeze is about 0.1 s. The `create_timer` argument question still stands, so the designer should rule on numbers taken at 120 fps.
3. **[P1][S] Re-validate WK-21 option A.** It is not needed: wall = tick with the display on. Retire the fallback note in BACKLOG.
4. **[P2][M] Residual stage-load spike (62-72 ms).** In-tree `_load_stage` costs 17-54 ms (Singularity is the worst), plus respawn and HUD work in the
   same tick. Option: build the next level off-tree during SCOREBOARD and swap it in at STAGE_INTRO, or spread the load over 2-3 ticks.
   Owner: gameplay-programmer.
5. **[P3][S] Log spam.** `_warn_once` is per renderer instance, so every stage load prints the missing-tuft and missing-flower `push_warning`
   with a full backtrace (17 times in one session). Make it static, or ship the decals.
6. **[P3][S] Fix the diagnostics skill §2.** `frame_time` (TIME_PROCESS) is **not** the last frame's process time. Godot reports the
   **max over the last ~1 s, including the render/swap wait**. It read 511 ms on ordinary 35 ms frames.
   Also update the golden draw-call count from 28 to about 75-80 (current arenas).
7. **No renderer change.** Compatibility/GL holds 120 fps. Vulkan Mobile, ANGLE+no-vsync and exclusive fullscreen also measured
   about 119 fps, so they are there if a future player machine needs them.

**Regressions vs last report:** none. The "16-30 FPS" figure was a measurement-environment error.
**Growth across rounds:** none (nodes bounded; texture memory +52 MB, one-time, from the fix).
